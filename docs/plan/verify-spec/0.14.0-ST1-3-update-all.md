# VERIFY-SPEC — ST1~ST3 `gbc update --all` + 도그푸딩 hook 보존

## 변경 파일
- `src/install.ts` — `isValidPreCommand`(신규 private) · `planUpdateTargets`(신규 export) · `UpdateTarget`
- `src/cli.ts` — `cmdUpdate` 재작성(--all·fail-soft·요약) · help 텍스트
- `README.md` — 명령 표
- `test/unit.test.mjs` — 신규 8건(normalizeHooks 3 · hasStalePreToolUse 1 · planUpdateTargets 4)

## 구현 결정
- **보존 판정 기준 = "가리키는 cli.js가 실존하는가"**. 사용자 선택(AskUserQuestion)에 따라 「덮어쓰기」·「--force」 기각.
  실존을 기준으로 둔 것은 자가치유 때문 — 가리키던 dist가 사라지면 다음 init이 전역 경로로 되살린다.
- **단일 술어 공유**: `normalizeHooks`(쓰기)와 `hasStalePreToolUse`(읽기)가 `isValidPreCommand`를 함께 쓴다.
  한쪽만 고치면 "정규화 안 하는데 stale 나그" 모순이 남는다 → 두 판정의 일치를 회귀락으로 고정.
- **순회 대상 산정을 순수함수로 분리**(`planUpdateTargets`) — 스폰은 테스트가 어려워 "어디에 돌릴지"만 결정론화.
- **경로는 spawnSync의 cwd 옵션으로만** 전달(명령 문자열 미보간). repos.json은 타 프로세스가 쓰는 전역 파일.
- fail-soft + 마지막 실패 목록 + exit 1. 전역 npm 설치는 1회.
- 기존 테스트 1건의 단언 문구를 갱신함(`init 생략` → `건너뜀 + 사유`). **약화가 아니라 강화**(사유 표면화까지 단언).

## 미확인 사항
- Windows 실기 미검증. `existsSync`·`resolve`는 크로스플랫폼이나, hook 명령의 경로 표기(백슬래시)가
  `/^node "(.+)" hook pre-tool-use$/`에 정확히 걸리는지는 리눅스에서만 확인했다.
- 레지스트리에 **심링크 디렉토리**가 등록된 경우를 별도로 다루지 않았다(`existsSync`는 따라간다).
  repos.ts는 절대경로 필터만 하고 lstat 심링크 거부는 다른 경로에 있다 — 이 조합이 충분한지 미확인.
- `--all` 실행 중 사용자가 중단(Ctrl+C)했을 때 일부 repo만 init된 중간 상태가 남는다. 멱등이라 재실행으로
  수렴하지만 명시적으로 다루지 않았다.
