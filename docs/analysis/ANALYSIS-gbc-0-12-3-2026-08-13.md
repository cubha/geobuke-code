## 3. 결함

### ✅ F-1 (적발 → 같은 날 수정 완료) — P2a 효과가 프로덕션 형상에서 재현되지 않았고, eval이 도달 불가능한 입력을 검증하고 있었다

> **상태**: 2026-08-13 수정 반영(커밋 `5520fe3` 형상 계약 락 · `0945de3` 규칙 재작성). 아래 §진단은 수정 **전** 관측 원문이며, 처방·결과는 말미 「수정 결과」에 있다.

**현상.** 이 배치의 존재 이유는 "이미 적용된 형제 케이스를 missing에서 빼는 것"이다. eval 케이스 20이 그 증명 케이스인데, **케이스20이 judge에 넣는 문자열을 프로덕션은 절대 생성할 수 없다.**

| | 문자열 |
|---|---|
| eval case20 `applied_context` | `1. [src/admin/keys-page.tsx] 관리자 키 목록 페이지에 API 키 마스킹(끝 4자리만 노출) 렌더링 로직 **적용 완료** (최신)` |
| 프로덕션 `formatAppliedContext` 실측 출력 | `1. [src/keys-page.tsx] export function KeyRow({ row }) {\n  return <td className="key">{maskKey(row.key)}</td>;\n}\n… (최신)` |

전자는 **"무엇을 완수했다"는 계획 어휘의 서술**, 후자는 **원시 소스코드**다. `applied.ts summarizeAppliedEdit`는 `new_string`을 redact+400자 캡만 해서 그대로 돌려준다 — **요약을 만드는 코드가 구조적으로 없다.** digest는 편집 원문이 무엇이든 그대로 실린다(모델이 마침 서술형 주석을 쓴 편집이라면 우연히 전자에 가까울 수 있으나, 그건 설계가 아니라 사고다).

**인과 실측** (동일 `plan_spec`·`edit_diff`, temperature 0, 3표본):

| 입력 형상 | 판정 | 기대 |
|---|---|---|
| A) eval 케이스 형상(요약형) | **pass 3/3** | pass |
| B) **프로덕션 실제 형상(원시 코드형)** | **block 3/3** | pass |
| C) 원장 없음(대조군 = case21) | block 3/3 | block |

**B ≡ C.** 프로덕션 형상에서 적용이력은 판정을 바꾸지 못했다. B의 차단 사유는 *"이미 적용된 편집(keys-page.tsx의 maskKey)은 마스킹 표시를 다루고 있으나, 암호화된 키를 복호화한 후 마스킹하는 통합 로직이 누락됨"* — 모델은 원장을 **읽었지만**, 원시 코드가 어느 계획 케이스를 충족하는지 스스로 단정하지 않고 새 반론으로 이동했다.

프로덕션 hook 종단(`gbc hook pre-tool-use`, 신규 워크스페이스 2개로 상태 격리)에서도 동일: 처치군·대조군 **둘 다 block**, 둘 다 `missing=["관리자 페이지에서 저장된 키를 마스킹해 표시한다"]`. 처치군 사유는 *"이미 완료된 편집 섹션에 KeyRow/maskKey가 있지만 **관리자 페이지 적용 여부가 불명확**"*. `appliedCount=1`이 이벤트에 찍혀 **배선은 살아 있음**이 동시에 확인된다 — 실패 지점은 전달이 아니라 **내용의 형상**이다.

**절대화하지 않는다 — 1회는 작동했다.** 같은 hook 종단의 초기 임시 fixture 실행 1회에서는 처치군이 이미 적용된 암호화 케이스를 실제로 missing에서 **배제**했다(`missing=["마스킹 표시"]` vs 대조군 `missing=["암호화 저장"]`). 즉 P2a는 *때때로* 작동한다. 그러나 fixture를 케이스20 수준으로 정제하자 재현되지 않았고, temperature 0 · 3표본에서는 0/3이었다. 정확한 표현은 **"효과가 없다"가 아니라 "효과가 재현되지 않는다 — 그리고 재현을 보증해야 할 회귀 케이스가 도달 불가능한 형상을 재고 있다"** 이다.

**계열.** 0.12.0 F-13(골든 replay가 `currentFileContent` 미전달로 flip0 = 거짓안심)과 같은 계열. 회귀 스위트가 실 경로가 아닌 형상을 재고 있으므로 green이 안전 신호로 성립하지 않는다.

**대조 근거 — grep 근거주입(P2b)은 왜 되는가.** `GATE_SYSTEM` ★★★ 규칙은 원시 grep 라인에 대해 *"그 문맥이 해당 케이스를 실제로 구현하고 있다면 missing에서 제외하라. 심볼만 존재하고 로직이 없다면 여전히 침묵 누락"* 이라고 **원시 코드를 읽는 법**을 명시한다. 반면 신규 ★ 적용이력 규칙은 *"이 목록의 편집에서 이미 다뤄졌다면"* 이라고만 해서, 내용이 원시 코드라는 사실도, 판독 기준도 주지 않는다. 규칙은 요약형을 전제하고 쓰였고 데이터는 코드형이다 — **규칙과 데이터의 형상 불일치**가 근본원인이다.

**수정 방향(택1 아님 — ①③은 필수, ②는 대안 축):**
1. **필수** — `test/cases.json` 20번의 `applied_context`를 프로덕션 실출력 형상으로 교체. 지금 상태로는 케이스20이 무엇도 보증하지 않는다.
2. 형상 정합 중 택1:
   - (a) **규칙을 데이터에 맞춘다** — ★ 규칙을 ★★★와 동형으로 재작성(원시 코드 판독 기준·"로직이 실제로 있으면 제외" 명시). 판정변경 0건, 프롬프트만 수정.
   - (b) **데이터를 규칙에 맞춘다** — 원장 digest를 요약형으로 승격. 요약 생성 주체가 필요(PostToolUse에서 LLM 호출 = 편집마다 과금·지연, 채택 시 별도 설계 필요) → 비용상 (a) 우선.
3. **필수** — 수정 후 §3의 A/B/C 3형상 실측을 재수행해 B가 pass로 넘어가는지 확인(대조군 C는 block 유지여야 인과격리 성립).

#### 수정 결과 (2026-08-13)

ⓐ와 (a)를 함께 반영했다. (b)(digest 요약형 승격)는 채택하지 않았다 — PostToolUse에서 LLM 호출이 필요해 편집마다 과금·지연이 붙는데, (a)로 충분함이 실측됐다.

**처방 1 — 케이스 생성 경로 변경(구조적 재발 차단).** `cases.json`이 조립된 문자열을 적는 것을 금지하고, 프로덕션 hook이 받는 것과 같은 **raw 편집 입력**(`applied_edits`)만 선언하게 했다. 조립은 프로덕션 함수(`buildAppliedEntry`→`formatAppliedContext`)가 수행한다(`src/eval/applied-input.ts` 신규). `test/eval-cases.test.mjs` 5건이 이 규율을 기계로 강제한다 — 문자열 직접 기입 금지·프로덕션 함수 통과 여부·**바이트 동일성**·인과격리쌍 존재·무신호 방지. 부수 효과로 케이스20이 이제 400자 캡과 `…(절단됨)`까지 프로덕션과 동일하게 재현한다.

## 4. 델타 아키텍처 평가

### 구조

```
src/applied.ts (신규 183줄)      ← 순수 부품 + .gbc/applied.json I/O
   ↑ 단방향(순환 방지, evidence.ts 관례)
src/gate-core.ts                 ← deps.loadApplied 주입 · self-file 필터 · 예산 조립 · 계측
src/hook.ts  runPostToolUse      ← 기록측(quiet fail-open)
src/judge.ts buildUserMessage    ← [이 작업단위에서 이미 적용된 편집] 섹션
src/install.ts / notice.ts / cli.ts ← 설치·안내·수명주기(gbc done)

src/tui/bang.ts (신규 219줄)     ← 파서(순수) / 러너(spawn seam) / 포맷터(순수)
   ↑ app.tsx editor-submit 최상단 분기(기존 프롬프트 경로와 완전 분리)
```

| 항목 | 평가 | 근거 |
|---|---|---|
| 레이어 분리 | 높음 | `applied.ts`가 `gate-core.ts`를 import하지 않음(단방향). `isDocFile` 조합을 호출부(hook.ts) 책임으로 밀어 순환을 구조적으로 차단 |
| 패턴 일관성 | 높음 | `GateDeps` 주입·`...meta` 키생략 스프레드·`ensureXHook` 멱등·`format*Context` 예산 조립 — 전부 기존 관례 재사용. 신규 관례 0 |
| 테스트 가능성 | 높음(단, F-1) | 순수/I-O 분리로 결정론 테스트 622줄 확보. **다만 순수부 테스트가 통과해도 형상 정합은 안 잡힌다** — F-1이 그 사각 |
| fail-safe 설계 | 높음 | P2a 실패 = 정보 없음 = 대조군과 동일(더 엄격해지지 않음). `!bash`는 판정 경로 미접촉 |
| 관측성 | 높음 | `appliedCount`/`appliedDropped`/`appliedFailed` 3축이 "없음"과 "못 읽음"을 구분(F-14 원칙 계승). 이번 검증에서 `appliedCount=1`이 배선 생존을 증명한 실사용 사례 |

### 강점

- **단방향 import 규율이 실제로 작동했다.** `applied.ts` 헤더가 순환 위험을 명시하고 `isDocFile` 조합을 호출부로 밀어낸 결정 덕에, `gate-core.ts ↔ applied.ts` 상호참조가 만들어질 여지가 없다.
- **`!bash` 안전기준이 관측으로 확정됐다.** 사용자가 잠근 요구(argv spawn)가 문서·코드가 아니라 실행 결과(`$HOME` 미확장, `|`·`>`·`;` 리터럴)로 입증됐다.
- **초기구현 버그가 잡혀 있었다.** maxBytes 초과 시 `kill()` 후 close 대기 → 실측 701ms 즉시 확정으로 수정됨(SubTask7).
- **계측이 검증을 가능하게 했다.** `appliedCount` 키 유무가 이번 F-1 진단에서 "전달 실패"와 "내용 부적합"을 가른 결정적 신호였다. 이 필드가 없었으면 오진했을 것.

### 약점

- **F-1** — 회귀 스위트가 실 경로 형상을 재지 않는다(F-13 재발). 순수함수 테스트가 아무리 촘촘해도 **"프롬프트에 실제로 어떤 문자열이 가느냐"** 는 축은 커버되지 않는다.
- **F-2** — 골든 replay 경로가 신규 필드에 대해 미실행.
- 원장 digest 400자 캡이 라인 단위 절단이라, 절단 지점이 문법 중간이면 모델 판독이 더 어려워진다(F-1과 같은 뿌리).
